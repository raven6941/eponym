# Integration tests — implementation plan (issue #502)

Status: LANDED (branch `502-integration-tests`). All 4 scenarios green
under `xvfb-run -a npm run test:integration` on the dev VM, plus a CI job.

## What exists

- `runTest.js` — host-side launcher. Downloads + caches a pinned VS Code
  (`EPONYM_TEST_VSCODE_VERSION`, default 1.85.0 to match `engines.vscode`),
  seeds a FRESH throwaway `--user-data-dir` per run with
  `eponym.lspServerPath` from `EPONYM_TEST_LSP`, opens
  `fixtures/workspace.code-workspace` with `--disable-workspace-trust`,
  `--no-sandbox`, `--disable-gpu`, runs `suite/` inside the extension host.
  Environment quirks handled: (a) this VM's `tar` cannot chown archived
  files to uid 1000, so `ensureVSCode` tolerates the nonzero tar exit when
  the `code` binary extracted and stamps the `is-complete` marker;
  (b) a stale `1.85-main.sock` in a reused user-data dir crashes startup,
  hence the fresh profile per run.
- `suite/index.js` — sequential scenario runner, no mocha dependency.
- `suite/scenarios/01-activation.js` — opens `fixtures/hello.ep` as nim,
  asserts the extension activated via `onLanguage:nim` (polls 15s).
- `suite/scenarios/02-server-initialize.js` — `eponym.expandShed` on the
  shed fixture drives the extension's own `inlineClient` path
  (ensureServerBinary → spawn → initialize → didOpen → shedLayout);
  asserts the inline view renders.
- `suite/scenarios/03-diagnostics.js` — opens `fixtures/type-error.ep`
  as nim; the extension opens an LSP client for `.ep` files on open
  (`maybeStartEpClient`), the server answers didOpen with
  `textDocument/publishDiagnostics`; asserts a severity-Error diagnostic
  arrives via `vscode.languages.getDiagnostics`.
- `suite/scenarios/04-shed-roundtrip.js` — real selection change onto the
  `![basic]` marker line, `eponym.expandShed`, assert the inline view
  text appears, `eponym.collapseShed`, assert byte-identical restore.
  (This is the wiring the headless mocks explicitly do not cover.)
- `fixtures/` — `hello.ep`, `type-error.ep` (standalone `.ep` syntax;
  the server elaborates `.ep` text directly), `shed_basic.nim`
  (embedded syntax — shed blocks live in `eponymBlock`) plus its
  committed pre-generated `shed_basic.sheds.json` (`.gitignore` carries
  an exception; regenerated by `nim c` on the fixture).

## Product changes (src/)

- `protocol.ts`: `LspClient` takes an optional `onDiagnostics` callback
  receiving plain `ServerDiagnostic` JSON. Stays vscode-free (the node
  `smoke` test requires it) — the VS Code mapping lives in extension.ts.
- `extension.ts`: a `DiagnosticCollection("eponym")` fed by
  `forwardDiagnostics`; the document-client construction passes it.
  `.ep` files get an LSP client on open (`maybeStartEpClient`, deduped
  via `documentClients`, shut down on close) — standard language-server
  behavior, and what makes scenario 03 meaningful.

## CI job (`.github/workflows/ci.yml`)

`integration-tests` on `ubuntu-latest`: choosenim setup, `nim c
src/eponym/lsp.nim`, cache of `editors/vscode/.vscode-test/`,
`npm ci` + `npm run build`, then
`EPONYM_TEST_LSP=$GITHUB_WORKSPACE/src/eponym/lsp xvfb-run -a npm run
test:integration`.

## Constraints (unchanged)

- No VSIX packaging for the test run (`runTests` takes
  `extensionDevelopmentPath`).
- Interactive UX (box-vanish, cursor feel) stays a human session (#5).
- Scenarios never touch the developer's real VS Code profile.
