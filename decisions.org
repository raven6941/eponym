* 2026-10-07 — Experiment 1: surface syntax front end

  Context: two front ends built for the same preterm AST
  (=preterm.nim=): (a) hand-written string parser (=parse_surf.nim=,
  ~250 lines, full syntax: =?=, =Pi=/=Sig= binders, =let=, pairs);
  (b) Nim-AST macro (=mac_surf.nim=) mapping proc definitions.
  Both produce identical ASTs for twice/const/pairSwap (tested).
  Findings:
  - (b) reuses Nim's parser and gets locations free via lineInfoObj,
    but Nim's grammar constrains the surface: =?= unusable (needs
    =Univ=), Nim keywords unavailable as names (=const= failed),
    dependent binders need encodings (=Sig(u, A, B)=), =let= sections
    don't map to term-let.
  - (a) has full syntactic freedom and precise errors, but the
    surface is a string (no IDE support, we own the lexer).
  - Nim ="""= strips the leading newline (location accounting note);
    =bindSym= needs a NimNode, not a string.
  Decision: hybrid for Experiment 2 — string literal *through* a
  macro: full syntax freedom + compile-time elaboration/checking
  inside macro expansion (the Turnstile analogy), errors via
  =error()= at string-relative locations. (b) kept as reference for
  Nim-embedded fragments.
  Consequences: Experiment 2 builds =ett"..."= macro on =parse_surf=;
  =mac_surf= stays as an alternative front end, not the main path.

  Addendum 2026-10-07 (Nimony review): Nim 3 replaces Nim 2 macros
  with compiler plugins (separate programs transforming NIF trees —
  different API: =NifCursor=//=NifBuilder=, not =NimNode=). This
  *confirms* the hybrid choice: the surface language lives in
  strings parsed by our own code, so only a thin wrapper is
  Nim-2-specific and would need porting. The =v2= import plugin
  (shells out to a Nim 2 compiler) provides a compat bridge, so no
  pre-porting. Rule: keep the macro layer thin (parse string →
  elaborate → emit); avoid deep =NimNode= coupling (=getImpl=,
  =bindSym= internals, hygiene edge cases). See
  [[https://github.com/raven6941/notes/blob/main/nimony-nim3-macro-future.org][Nimony note]].

* Experiment 5b: conversion in checkTm (2026-10-07)
  - Closed the documented gap: =checkTm='s inferred-vs-expected check
    used syntactic Miller unification, so =Vec A (add zero n)= against
    =Vec A n= was rejected even though the =wRed= rules make them
    convertible. New =convElab= in =elab.nim=: zonk both sides; if
    unsolved metas remain, fall back to pattern unification (evaluation
    cannot solve flex constraints, and =unify= is the only thing that
    can); otherwise evaluate both sides in one shared identity
    environment — free variables become fresh neutral parameters via
    the core's =freshPara=, so open terms evaluate soundly — and run
    the core's =areEqual= guided by =*=, mirroring the core's own
    =check=. =freshPara= and =areEqual= are now exported from
    =ett_init.nim= (pure =*= additions, no behavior change).
  - Only the =else= branch of =checkTm= changed (the genuine
    inferred-vs-expected check). Ascriptions, =let= bodies, =pkAnn=,
    and the =ensurePi/=ensureSi= domain checks keep =unifyElab= —
    those are solving positions, and conversion must not run while
    metas are still being assigned.
  - Result: =vnil : Vec Nat (add zero zero)=, the open-context
    =constNil=, and full =Vec append= (motive with =add= in the
    indices: the nil case needs =add zero n ≡ n=, the cons case needs
    =add (suc i) n ≡ suc (add i n)=) all elaborate; genuinely
    different indices are still rejected ("not convertible"). The
    test's =add= recurses on its *first* argument so the rules fire
    under a neutral second argument. All 8 suites green, including
    the compile-time =ett= macro suite (the new path runs =eval= /
    =areEqual= inside the Nim VM without trouble).
  - Honest deltas: (1) conversion ignores the implicit/explicit
    binder flag — =Whnf= drops =impl=, while =unify= checked it —
    so strictly more programs are accepted here; consistent with the
    core checker's =areEqual=. (2) The mixed case — an unsolved meta
    *under* a redex, e.g. =Vec A ?m= vs =Vec A (add zero ?m)= —
    still fails: the fallback =unify= hits the occurs check. Fixing
    that needs constraint postponement, Experiment 6+ territory.
    (3) One test expectation updated: the =fst (snd p, fst p)=
    program's error changed from "cannot unify" to "not convertible"
    — same rejection, better message.
  - Turnstile+ connection: this is their elaborator's conversion
    check, except ours reuses the *core* evaluator and conversion
    relation rather than a separate elaboration-time one — one
    conversion relation for the whole system, as the paper's
    dependent-type story wants.

* Experiment 5 results (2026-10-07)
  - =data= declarations desugar to Experiment 4's
  - =data= declarations desugar to Experiment 4's
    =postulate=/=elim=/=red= and elaborate through the same path.
    =data Nat= generates the type former, constructors, eliminator,
    and reduction rules; =add two two= reduces to 4. =data Vec (A :
    ?)= is an indexed family; the generated =vecElim= computes
    (length of a 2-vector reduces to 2). All 8 suites pass.
  - Key design: the desugarer generates =red= rules with *dummy
    index variables* (=idx0=) in the eliminator's index positions.
    The contractum never mentions them; =fireRed='s spine
    convention already accounts for them. This avoids unifying
    indices during rule elaboration — the constructor's indices
    are determined by its return type, not by pattern unification.
  - Constructor patterns may reference already-bound params
    (=(nil A)= where =A= is the eliminator's param). =elabRedDecl=
    now allows leading already-bound variables in the scrutinee
    pattern (=nParams=); =fireRed= skips them when building =cargs=.
    The =RedRule= stores =nParams= for this.
  - De Bruijn frame bug (again!): =fireRed='s =cargs= were in
    application order but the template expects innermost-first.
    Single-argument constructors (=suc=) mask it; =cons= (3 args)
    exposed it. Lesson, third time: every substitution must match
    the context's variable order — test with ≥2 variables,
    *including constructor arguments*.
  - Limitation (honest): full dependently-typed programming like
    =append= with =add= in the return type needs *conversion* in
    =checkTm=, not just Miller unification. =add zero n ≡ n= holds
    by the =wRed= rule, but =unifyElab= is syntactic (up to beta)
    and doesn't unfold definitions or fire rules. The =data=
    mechanism itself is sound; the typechecker's conversion is
    the gap. Fixing it means making =checkTm= use the evaluator
    (conversion) for the inferred-vs-expected check, not just
    unification. That's the next experiment's work.
  - Turnstile+/Levitation connection: our =data= is Dybjer-style
    (generative, per-family eliminator). Levitation's =Desc=
    universe (datatypes-as-data) is the alternative: elaborate
    =data= to codes, keep the core closed. Worth an experiment.

* Experiment 4 results (2026-10-07)
  - Built extensible reduction: =postulate= (parameter-like global),
    =elim= (eliminator with a reduction rule table), and =red=
    (one constructor case) declarations. New constructs bring their
    own reduction rules; the core evaluator was extended once (a
    =wRed= whnf + firing logic in =applyWhnf=), never per-construct.
    Demos: Bool eliminator (=not true= reduces to =false=) and Nat
    eliminator with constructor arguments (=add two two= reduces to
    =suc^4 zero=, verified by evaluation). All 8 module suites pass.
  - Key design decision: *the rule lives in the value, not in a
    threaded registry.* The eliminator's R node carries a =wRed=
    whnf holding the rule table; =applyWhnf= consults it when the
    eliminator is fully applied and the scrutinee is
    constructor-headed. This avoided threading a registry through
    =eval=/=check=/=infer=/=areEqual= (~12 procs, the
    Supply-precedent alternative). Stuck eliminators (neutral
    scrutinee) rebuild as =wRef= neutrals, so conversion needs no
    new neutral case; only partial applications stay =wRed= (with a
    =structuralEq= case).
  - De Bruijn frame bug (caught by the Nat test, invisible to Bool):
    the contractum template's context is innermost-first =[n, s, z,
    C]=, but =fireRed= passed the spine outermost-first =[C, z, s,
    n]=. Single-variable templates (Bool) pass by accident;
    multi-variable ones scramble. Lesson, again: every
    substitution must match the context's variable order — test
    with ≥2 variables.
  - The unifier needed head-beta: eliminator motives are lambdas,
    so =C true= with =C := lam u. Bool= is a redex the syntactic
    unifier couldn't see through. Added =unifyHead= (unfold solved
    metas at head/function position + beta; no delta-unfolding, so
    rigid heads stay rigid).
  - Limitations (honest): the contractum is *trusted* — elaborated
    in inference mode, not checked against the instantiated motive
    (a production system would; that's Experiment 5+ territory).
    =red= patterns require distinct bare variables; the parser
    doesn't support multi-name binders =(m n : Nat)=. Non-terminating
    rules (=red f x := f x=) would loop the evaluator — the rule
    author's obligation, as in any rewrite system.
  - Turnstile+ comparison: our =red= is =define-red= without
    reflected names — rules are keyed by constructor head, and
    neutrals rebuild as =wRef= rather than carrying a
    =reflect-name= property. Sufficient because our rules are
    first-order constructor patterns; reflected names would matter
    for higher-order patterns.

* Experiment 3 results (2026-10-07)
  - Built =unify.nim= (Miller pattern unification: spine inversion,
    occurs check, eta, zonk) + rewrote =elab.nim= as full bidirectional
    =inferTm=/=checkTm= with implicit-argument insertion. Demos pass:
    =polyId {A} (x:A)=, =constI {A}{B}=, =pairSwapI {A}{B}= applied
    *without* type arguments (=polyId <>=, =constI <> <>=); unannotated
    =lam x. x= and =let f = lam x. x in f <>= infer. All Experiment 2
    programs still elaborate; =ett= macro accepts/rejects at compile
    time. All 7 module test suites pass.
  - Demos adapted from the plan: ETT core has no vectors and no
    identity type, so =refl=/=cong=/vector-=append= are inexpressible.
    The *mechanism* under test (implicit Pi insertion + Miller
    unification solving the implicit args from explicit ones) is
    identical for =polyId=/=constI=; vectors would only add datatype
    boilerplate (Experiment 5). Recorded, not hidden.
  - Metas live in the core =Term= (=tMeta= with occurrence spine) but
    are zonked *before* the core's =check= ever runs; =eval=/=infer=
    raise on =tMeta= as a safety net (never fires on the success
    path). The core's soundness story is unchanged: what it checks is
    meta-free. =impl= flags on Pi/Si/Lam are elaborator metadata —
    preserved by every core structural operation, never interpreted.
  - No surface syntax for explicit implicit application: implicits are
    always inferred/inserted. Holes =_= elaborate to metas; leftover
    unsolved metas (including in types) are errors carrying the
    creation location.
  - Two de Bruijn frame bugs found by testing, both worth remembering:
    (a) extending the elaborator context must *weaken every stored
    type* into the new frame (not just the new entry) — =ext= now maps
    =weaken= over all entries; (b) =subst='s old "closed substitute"
    contract was wrong for open terms: the substitute must be weakened
    when going under binders (was invisible before because the only
    substitutes were closed =R= nodes). Both are the same lesson:
    every operation that moves a term across a binder boundary must
    adjust the frame — audit all of them when touching substitution.
  - The elaborator no longer needs =Supply= (fresh metas use the
    meta store's own counter); only =elabCheck= keeps it for
    =newDefRef= and core checking. Unification runs on syntax (Terms),
    not values — rigid-rigid under binders is direct structural
    recursion since de Bruijn makes V0 = V0.
  - Proceeded on the current core per the Track B memo's *proposed*
    resolution (Experiment 3 is core-independent elaborator work);
    the memo still awaits Aaron's ratification.

* Experiment 2 results (2026-10-07)
  - Built =elab.nim= (bidirectional-lite elaborator) + =ett_mac.nim=
    (=ett"..."= macro). All Experiment 1 programs (=twice=, =constFn=,
    =pairSwap=) elaborate and check; ill-typed programs fail compilation
    with errors naming surface terms at string-relative line/col.
  - Pairs need an expected Sigma type: synthesis cannot invent the
    range, so =elabChk= takes the expected type as a *Term* and reuses
    the expected Sigma's scope directly as the pair's =pScope= (same
    de Bruijn frame: one binder over the context). Verification stays
    with the core's =check= — the expected type only guides.
  - Cross-def references work via closed =R= nodes (=newDefRef=);
    later defs mention earlier ones.
  - Unannotated lambdas/lets rejected in synthesis mode; nested
    ascriptions guide but are not separately verified (Experiment 3:
    full bidirectional check).
  - Macro-in-VM constraint (major find): Nim's VM cannot capture
    module-level =var=, so the core's global =freshSupply= broke
    compile-time checking ("cannot evaluate at compile time").
    Fix: threaded an explicit =Supply= through =infer=, =check=,
    =synth=, =structuralEq=, =areEqual= (the paper's Checking-monad
    threading — the global was our simplification). Core is now
    reentrant; all 16 existing tests pass unchanged in behavior.
    Lesson for macro-based elaboration in Nim: no global mutable
    state anywhere on the compile-time path.
  - Export facade added to =ett_init.nim= (=Const*=, =TermKind*=,
    =Term*=, =Value*=, constructors, =tmC*=, =check*=, =vStar*=,
    =newDefRef*=); elaborator lives in its own module.

  Branch pruning alone does not pay for interpretation overhead; the
  payoff requires compiling residuals (option b), e.g. generalizing

  This is now the concrete form of #19's "leaves experimental status"
  question.

* 2026-10-08 — Issue #35: residual compilation flips #19's negative result (1.90x)

  Follow-up to #19's decision ("the payoff requires compiling
  residuals"). =src/staging/relcompile.nim= compiles each
  =SpecCtx.specs= entry to a native Nim proc
  =name(p1..pn: RTerm): Goal=: =rgEq/rgNeq= -> ===/=/=,
  =rgConj/rgDisj= -> =conj/disj=, =rgFresh= ->
  =fresh(proc(rc_fK: RTerm): Goal = ...)=, =rgCall= -> direct proc call
  wrapped in a run-time thunk
  =proc(rc_s: State): Stream = name(args)(rc_s)=. The thunk preserves
  =toGoal='s lazy-expansion semantics (callee goal-tree construction
  happens at goal-run time, so recursive calls can't infinitely recurse
  at goal-build time) while eliminating the per-call =substAtom= walk
  and =relEnv= lookup. The specializer runs at compile time inside the
  =stagedTypeoProcs= macro (staging-plan.md: "Generator = Nim macro"),
  so specialization + compilation is one =nim c -r= step; a
  =stagedTypeo(tm, ctx)= template names the top checker. Residual calls
  to *unspecialized* relations are a compile-time error, not silent
  wrong code.

  Results (=src/staging/test_compiled_typeo.nim=, same 9-term corpus as
  #19): differential correctness PASSES (9/9 agree, all match
  expectations); wall-clock *compiled vs unstaged = 1.90x speedup*
  (9.12ms -> 4.79ms per-iter total), and *compiled vs interpreted
  residual = 3.88x*. #19's 0.49x was interpretation overhead, exactly
  as diagnosed — compilation removes it and the branch-pruning savings
  show through. Biggest wins on failing cases (2.18x on =lam(0) : nat=):
  pruning pays most where search explores dead branches.

  Lesson for the record: staging's value was invisible until the
  residual was compiled. An interpreted residual is a pessimization;
  the 1st projection only counts once it's native code. This unblocks
  the "leaves experimental status" question for relational staging and
  is the prerequisite for Phase 4 (stage the elaborator and measure).

  Nim gotchas hit: (a) mixing =result =-assignment in one =case= branch
  with implicit returns in others silently turns the implicit ones into
  statements ("has to be used (or discarded)") — use explicit =result =
  in every branch; (b) hand-built =nnkProcDef= forward declarations
  need 7 children (name, genericParams, pattern, formalParams, pragmas,
  extra, body), not 6 — =treeRepr= on a parsed forward decl is the
  ground truth; (c) =quote= gensyms template/proc *names*, so the entry
  template is built with manual AST.

  * 2026-10-08: Issue #32 — clause-style definitions compile to
  eliminators (MVP). =def add : Nat -> Nat -> Nat= with =| zero n = n=
  and =| (suc m) n = suc (add m n)= elaborates to a =natElim=
  application; =add two two= evaluates to 4. Coverage (missing
  constructor) and overlap (duplicate constructor) are located
  compile-time errors.

  Design choices: (a) patterns are surface atoms — constructor
  applications need parens, =(suc m)=, so =zero n= parses as two
  patterns; (b) recursive calls =f ... y ...= on a pattern variable
  become IH applications syntactically at the PreTerm level, before
  elaboration; (c) whole thing done at PreTerm level then fed through
  the existing =elabDefDecl= — no duplication of elaboration logic.

  MVP limits (documented, not silently): non-indexed data only
  (=append= on Vec needs indexed motives), scrutinee must be first
  explicit arg, no nested patterns, no catch-all variable clause,
  no =ettDefs= macro-front-end support (string parser is primary).

  Lesson: compiling clauses to eliminators (rather than adding a
  native case-splitter to the core) keeps the trusted core small —
  the same argument as the embedding thesis. The elaborator does
  the work once; the core never learns pattern matching.

* 2026-10-09 — Issue #36: structural recursion as the termination criterion

  Criterion chosen: syntactic structural recursion. A recursive call is
  accepted iff its scrutinee-position argument is a bare variable bound
  by the LHS pattern — a direct subterm. Implemented twice: =checkStructuralRec=
  over =PreTerm= for =red= rules (before the rule is registered), and
  =checkClauseTermination= for #32 clause definitions (after IH-rewriting;
  any surviving self-reference is non-structural).

  Alternative considered and deferred: BelowD / course-of-values, where
  termination holds by construction because recursive data is
  internalized as its own course-of-values. More general (accepts
  e.g. course-of-values recursion that isn't syntactically structural)
  but requires reworking the data representation; the syntactic check
  covers the cases that matter now (=add=, =append=, =map=) and is far
  cheaper to implement.

  Two bugs found while building the clause checker: (1) non-structural
  self-calls in clause bodies previously fell through IH-rewriting and
  failed later as confusing "unbound variable" — now a located,
  name-aware termination error; (2) =replaceRecCalls= rewrote =f= on a
  pattern variable at *any* spine position, silently miscompiling
  e.g. =badm m n= into an ill-typed IH application — now only the
  scrutinee (first) position triggers rewriting, and anything else is
  rejected by the termination check.

  Corpus: 10 terminating definitions accepted, 8 non-terminating
  rejected (5 =red=-rule shapes + 3 clause shapes), all under the test
  timeout — no hangs. Rejection messages name the definition and the
  offending argument; no de Bruijn or rule-number leaks.

* 2026-10-09 — Issue #32: indexed clause definitions

  The MVP's "non-indexed only" limit is lifted. The motive now abstracts
  over the data family's indices: =C := lam (i0:Idx0)... . lam (_:D params
  i0..). Pi (rest...). Ret[i:=idx]=. Each method refines the scrutinee's
  index variables to the constructor's return indices (=nil: m:=zero=,
  =cons: m:=suc k=) via capture-avoiding =substPre= (new: =freeVarsPre=,
  =allNamesPre=, =substPre= — capture-avoiding PreTerm substitution).

  Design points: (a) scrutinee can be at any explicit position (not just
  first); the eliminator is applied to params, motive, methods, indices,
  scrutinee, then rest args in order. (b) Data parameters supported
  (=Vec A=); implicit params get metas solved by unification. (c) IH
  types are the motive tail with index binders substituted by the
  recursive arg's indices. (d) Pattern variables must not shadow
  telescope binders — a located error, since the method rebinds rest
  implicits by tele names.

  =vappend : Pi {A}. Pi {m n}. Vec A m -> Vec A n -> Vec A (add m n)=
  elaborates and computes; a RHS that confuses indices is rejected by
  conversion (=add zero n= must reduce to =n=, which it does via the
  clause-compiled =add='s eliminator).

  Remaining #32 limits: no nested patterns, no catch-all variable clause,
  no =ettDefs= macro-front-end support.

* 2026-10-09 — Issue #41: equality as overridable effect (handler stack)

  The elaborator's conversion (=convElab=) is now an effect-raising site
  in the Andromeda sense. Design, after the issue's plan:

  - Choke points: every conversion goal funnels through =convElab= (the
    infer-then-check boundary in =checkTm= and the =refl= tactic), so
    there is exactly one effect-raising site.
  - Interface (=unify.nim=): =ConvHandler= is an object with a =decide=
    closure returning =cvDischarged= / =cvDeclined=, plus a =coreValid=
    flag. Handlers decline goals they cannot decide; only the default
    handler at the bottom of the stack raises. Nim closures cannot
    capture =var= parameters, so instead of a =next= closure the driver
    loop in =convElab= simply tries the stack top-down — same semantics,
    no capture problem.
  - Dynamic scoping: =withConvHandler(ms, h, body)= pushes =h= for the
    dynamic extent of =body= (try/finally pop). =elabCheck= also takes an
    optional whole-program handler list. No algebraic effects needed.
  - Default handler (=defaultConv=): the old Experiment 5b conversion
    verbatim (core evaluator + =areEqual=, same error messages), plus
    recording successes in =ms.convCache=. With an empty stack the full
    test suite is green with zero accept/reject changes.
  - Trust model (the key decision): =elabDefDecl= step 3 re-verifies each
    definition with the bare core's =check=. A =coreValid=false= handler
    (a domain decision procedure) deliberately extends conversion beyond
    the core, so for definitions where such a handler discharged a goal
    (=ms.extDischarges= counter) step 3 is relaxed to evaluation — the
    elaborator's =checkTm= already validated with the extended
    conversion. Installing the handler is an explicit, dynamically-scoped
    trust extension; this is the Andromeda semantics (the core's equality
    is extensible by installed handlers). =coreValid=true= handlers
    (the cache: it only replays goals the default handler proved) keep
    the backstop in force.
  - Two handlers shipped: (1) =cacheConvHandler= — the Experiment 10
    cache as an opt-in scoped procedure: identical accept/reject on a
    Vec-heavy corpus vs the default (6 decls; default 0.038s, cache
    0.035s on this workload — the corpus is too small for the cache to
    win; a conversion-heavy benchmark is future work). (2)
    =natArithHandler= — linear Nat equations over ={zero, suc, add}= via
    normalization to =c + Σ kᵢ·xᵢ=, with congruence under =Eq= (the
    inferred-vs-expected check compares =Eq= types, not just sides).
    Discharges =add n (suc m) ≡ suc (add n m)=, =add n zero ≡ n=,
    =add n m ≡ add m n= for neutral =n, m= — all stuck for the core's
    NbE. Wired as the =by arith= tactic. Scoping pinned by tests: =by
    refl= still rejects the open goal, and =by arith= rejects false
    goals (=zero ≡ suc zero=).
  - Soundness status (honest): the arithmetic handler is a *trusted*
    decision procedure — each normalization step is a lemma provable by
    induction (add-zero-right, add-suc-right, AC of +), complete for
    linear equations over (ℕ, 0, suc, +), and it declines everything
    outside the fragment — but it does not return proof evidence for the
    core to validate. Evidence-returning handlers (proof terms checked
    by the core) are the documented next step.
  - Incidental finding: elaborated terms are only alpha-equivalent
    across cache/no-cache runs, because a cache hit skips =freshPara=
    calls and renumbers later fresh IDs. Accept/reject is identical;
    the test asserts names/length, not term strings.
  - Cache benchmark at scale (=src/bench_conv_cache.nim=, 2026-10-09):
    62-decl corpus (vappend of literal vectors + =by refl= on large add
    equations), 17,205 conversion goals, 99.6% hit rate — speedup only
    1.07x (9.94s -> 9.26s); all-distinct-numeral corpus still 98.8% hit
    rate (goals recur structurally: clause motives, implicit insertion),
    1.01x. Reading: the memo key is =$ctxLen & ":" & $a & " === " & $b=,
    rendered on *every* goal, and that rendering costs nearly as much as
    the NbE it skips for small goals — the cache only pays when
    per-goal conversion dominates key rendering. Two consequences:
    (a) the current cache is a correctness-preserving opt-in with
    ~free worst case, not a performance feature yet; (b) making it win
    needs cheaper keys (hash-consed term identity instead of string
    rendering) or targeting only expensive goals. Both are future work;
    the benchmark stays as the regression harness.

  Context: GH #17 acceptance required staging a real ETT term with

  specialization ever happened; =stage_ett_demo.nim= now drives it

** #28 architecture: typed API over untrusted backend (2026-10-09)
  Source: Wu & Xi 2017 ("Dependent Session Types", CONCUR) — curated to
  notes/wu-xi-dependent-session-types-2017.org, with the reusable idea at
  notes/typed-api-untyped-backend.org.
  Their ATS-to-Erlang pipeline splits the implementation in two: a typed
  session API (linear/dependent types checked) plus an untyped runtime
  backend (does the message passing, not verified). The guarantee lives
  at the boundary — well-typed API use cannot violate the protocol.
  For #28 this is the target architecture: the Eponym session API
  (protocol types checked at elaboration time) over plain Nim runtime
  functions (unchecked). Protocol violations are compile errors; the
  runtime is ordinary host code with zero type-system overhead. The
  backend is trusted for liveness, not safety.
  Companion reading: Toninho/Caires/Pfenning 2011 gives the logical
  foundation (session types as linear logic, proof irrelevance to avoid
  communicating proofs) — notes/toninho-caires-pfenning-dependent-session-types-2011.org.
