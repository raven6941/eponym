#+TITLE: Experiment plan: dependently typed Nim

* Overview

  The question (see [[file:research.org][research question]]) is attacked as a
  sequence of experiments, each with a question, a build, and a success
  criterion. Experiments are ordered so each one is meaningful even if the
  next fails — a negative result is a finding about Nim's metaprogramming,
  not a wasted build.

  Status of each experiment is tracked here. Per-experiment lab notes go
  under =experiments/= once started.

* Phase 0 — ETT core (done, 2026-10-06/07)

  Two implementations of Epigram's Type Theory in Nim, tested:
  - finally-tagless (=ett.nim=): =Sym[R]= interface, evaluator, printer,
    typechecker instances;
  - initial encoding (=ett_init.nim=): de Bruijn =Term= AST, glued values,
    =infer= / =check= / =areEqual=.
  Decision: the initial encoding is the elaborator target
  (see [[https://github.com/raven6941/notes/blob/main/encodings.org][encoding comparison]]).
  Repo: =github.com/raven6941/eponym=.

* Experiment 1 — Surface syntax via macros

  Question: what surface syntax can Nim macros deliver, and at what cost?

  Build two front ends for a tiny fragment (Π, λ, →, application, let,
  plus =?=, =1=, =O=), both producing the same preterm AST:
  - (a) string-literal DSL with a hand-written parser: full syntactic
    freedom, manual source-location tracking;
  - (b) Nim-AST shaping via macros/templates over =quote do:= blocks:
    constrained by Nim's grammar, but positions and hygiene come free.

  Success: =twice=, =const=, =pairSwap= expressible; parse errors point at
  source. Pick one front end (or a hybrid) for Experiment 2.

  References: [[https://github.com/raven6941/notes/blob/main/turnstile.org][Turnstile]] §2–3 (syntax
  patterns *are* the surface syntax); [[https://github.com/raven6941/notes/blob/main/nim-macros.org][Nim
  macro notes]].

* Experiment 2 — Compile-time elaboration and checking [DONE 2026-10-07]

  Question: can a Nim macro drive naming→de Bruijn elaboration plus our
  =infer= at compile time, with good errors?

  Build: elaborator =preterm → Term= (name resolution, de Bruijn indices),
  invoked inside a macro body; run =infer= there; on failure call
  =error(info, msg)= with surface locations attached.

  Success: well-typed programs elaborate silently; ill-typed ones fail
  compilation with errors naming *surface* terms. This is the Turnstile
  analogy checkpoint: their type rules run during expansion; our checker
  runs during expansion.

  Result: yes. =elab.nim= (bidirectional-lite: expected-type-guided pairs,
  cross-def refs via =R= nodes) + =ett"..."= macro (=ett_mac.nim=). Key find:
  Nim's VM cannot capture module-level =var=, so the core's global
  =freshSupply= was threaded explicitly through =infer= =check= =synth=

  Extension (2026-10-07): =ettEmbed= macro generates callable Nim procs
  from =ett= blocks. Each =def : Int -> ... -> Int= becomes
  =proc name(args: varargs[int]): int= that evaluates the elaborated term
  at runtime (via =ett_embed.callIntFunc=). Compile-time elaboration
  ensures well-typedness; runtime re-elaboration (cached) provides the
  evaluable terms. Enables embedding verified code in normal Nim programs.
  =structuralEq= =areEqual= (the paper's Checking-monad threading); core is
  now reentrant. Details in decisions.org.

  References: =ett_init.nim= (=infer=); [[https://github.com/raven6941/notes/blob/main/staging.org][staging]];
  [[https://github.com/raven6941/notes/blob/main/turnstile.org][Turnstile]] §2.

* Experiment 3 — Implicits, metavariables, unification [DONE 2026-10-07]

  Result: yes — it runs at macro-expansion time. =unify.nim= (Miller
  pattern unification) + bidirectional =inferTm=/=checkTm= with implicit
  insertion; =polyId <>=, =constI <> <>=, unannotated =lam x. x= all
  elaborate, zonk, and pass the core's =check=; =ett= macro
  accepts/rejects at compile time. Demos adapted (no vectors/identity
  type in ETT core — same mechanism on =polyId=/=constI=). Full
  findings in decisions.org ("Experiment 3 results").

  Question: the first genuinely hard elaboration step — can it run at
  macro-expansion time?

  Build: extend =Term= with metavariables; pattern unification (à la
  McBride/Norell); implicit-argument insertion; bidirectional elaboration
  (infer vs. check against an expected type).

  Success: the classic demos — =refl=, =cong=, vector =append= with
  implicit length arguments inferred, not written.

  References: [[https://github.com/raven6941/notes/blob/main/turnstile-plus.org][Turnstile+]] on Cur
  (unification, implicits); Kovács's
  [[https://github.com/raven6941/notes/blob/main/kovacs-elaboration-zoo.org][elaboration-zoo]] for the
  algorithm (port its ideas; consult Norell's
  [[https://github.com/raven6941/notes/blob/main/norell-thesis.org][thesis]] when the zoo's
  simplifications bite); Dunfield & Krishnaswami's
  [[https://github.com/raven6941/notes/blob/main/dunfield-krishnaswami-bidirectional.org][bidirectional
  discipline]] for how much can stay un-annotated.

  Risk note: this is where "convincingly" is won or lost. If unification
  at compile time is painful or slow, that *is* the result — record it.

* Experiment 4 — Extensible reduction ("normalization by macro expansion", Nim-style) [DONE 2026-10-07]

  Result: yes — =postulate= / =elim= / =red= declarations let new
  constructs bring their own reduction rules; the core evaluator
  grew one extension point (=wRed= whnf, rule in the value, no
  threaded registry) and is never touched per-construct. Bool and
  Nat eliminators reduce (=not true= → =false=, =add two two= →
  =suc^4 zero=); stuck scrutinees stay neutral; all 8 suites pass.
  Full findings in decisions.org ("Experiment 4 results").

  Question: can new constructs bring their own reduction rules, as in
  Turnstile+'s =define-red=?

  Build: a compile-time registry mapping head symbols to reduction rules,
  consulted by our evaluator; a declaration form that registers
  constructors, an eliminator, and its reduction rules.

  Success: add a new type former without touching the core evaluator;
  reduction stays confluent on the test suite.

  References: [[https://github.com/raven6941/notes/blob/main/turnstile-plus.org][Turnstile+]] §4.1
  (=define-red=, reflected names).

* Experiment 5 — Indexed inductive families [DONE 2026-10-07]

  Result: yes — =data= declarations elaborate to ETT core +
  eliminators via desugaring to =postulate=/=elim=/=red=
  (Experiment 4). =data Nat= and =data Vec (A : ?) : Nat -> ?= both
  work; the generated eliminators compute (=add two two= → 4,
  length of a 2-vector → 2). Constructor patterns can reference
  params; index positions use dummy variables. Full findings in
  decisions.org ("Experiment 5 results").

  Limitation: =append= with =add= in types needs conversion (not
  just unification) in =checkTm= — the unifier doesn't unfold
  definitions or fire =wRed= rules. That's the next gap to close.

  Resolved 2026-10-07 (Experiment 5b): =checkTm='s
  inferred-vs-expected check now uses =convElab= — full conversion
  via the core evaluator + =areEqual= when no unsolved metas remain,
  pattern unification otherwise. =Vec append= elaborates; details in
  decisions.org.

* Experiment 6 (complete 2026-10-07) — Tactics and reflection

  Question: can elaboration steps be reflected and scripted, Turnstile+-style?

  Only if 1–5 land. Their tactic system is the model
  ([[https://github.com/raven6941/notes/blob/main/turnstile-plus.org][Turnstile+]] §7).

  Concretization (proposed 2026-10-07, Lean 4-inspired): expose the
  elaborator's metavariable/hole state through a Nim API callable from
  macros, so users write elaboration-time tactics *in Nim* —
  metaprograms as ordinary compiled code, no VM. A =by= block runs Nim
  code that inspects goals and constructs =Term=s. The LSP server of
  Experiment 7 calls the same API the tactics use: one interface, two
  clients. See [[https://github.com/raven6941/notes/blob/main/lean4-theorem-prover.org][Lean 4 note]].

  Result (2026-10-07): Complete (basic). =by tac= syntax added;
  tactic registry with =assumption= (find matching hypothesis) and
  =refl= (prove =Eq= by reflexivity up to conversion). Tactics are Nim
  procs taking (goal, ctx, globals). Tests in =src/elab.nim=,
  example in =examples/14-tactics.ep=.

* Experiment 7 (complete 2026-10-07, basic) — interactive tooling without a bespoke editor

  Question: Epigram's productivity story depended on a purpose-built
  editor that understood sheds. Can LSP-based tooling fill the same gap
  for our embedded language?

  Background: a shed is an unchecked, user-owned region of the document;
  the system tracks elaboration status around it (white/yellow/brown).
  Modern equivalents are Agda/Idris holes and Lean 4's infoview — Lean 4
  is the existence proof that LSP can carry rich interactive dependent
  programming (see the
  [[https://github.com/raven6941/notes/blob/main/sheds-and-interactive-tooling.org][sheds note]]).

  Build: a small LSP server over our elaborator exposing diagnostics
  (elaboration status, stuck constraints, errors at surface locations),
  code actions (hole commands: refine, case-split, give), and hover
  (goals/types at metavariables).

  Success: a realistic interactive session — e.g. developing =Vec append=
  hole-by-hole — in a stock editor, no bespoke UI.

  Result (2026-10-07): Basic LSP server complete (src/lsp.nim).
  Stdio JSON-RPC; handles initialize, didOpen, didChange; publishes
  diagnostics from elaborator (parse + elab errors at surface locations).
  Tested with mock LSP session. Hover, code actions, and incremental
  sync are future work.

  This experiment is the tooling half of "convincingly": a useful system
  anyone would actually want to use needs it.

* Experiment 8 (complete 2026-10-07) — staged ETT evaluator via tagless-final

  Question: can our finally-tagless core do what Carette, Kiselyov &
  Shan showed — evaluator, compiler, partial evaluator as *instances*
  of one =Sym[R]= interface?

  Build: a staging/partial-evaluation instance for =ett.nim='s
  =Sym[R]=, producing residual code from ETT terms — a compiler from
  ETT obtained as just another interpretation. Keeps both encodings
  productive (initial for elaboration, tagless-final for staged
  interpretation) and prototypes the "stage the interpreter, get a
  compiler" moral for our core.

  Success: staged evaluation of a test program yields residual code
  with the interpretive overhead removed; the instance composes with
  the existing evaluator/printer/checker.

  Result (2026-10-07): Complete (basic). Added =newCodeGen(): Sym[string]=,
  an erasing code generator producing untyped lambda-calculus. The same
  =twice= term denotes a value (evalSym), pretty syntax (newPrinter),
  and executable code (newCodeGen) — staging as just another interpretation.

  References:
  [[https://github.com/raven6941/notes/blob/main/carette-kiselyov-shan-finally-tagless.org][Carette/Kiselyov/Shan
  2009]]; [[https://github.com/raven6941/notes/blob/main/encodings.org][encodings note]].

* Experiment 9 (complete 2026-10-07, basic) — erasure-aware elaboration (QTT-lite)

  Question: can we get QTT's killer feature — erasure — with a
  weeks-scale experiment instead of a theory change?

  Build: add 0/1/ω multiplicities to binders in the ETT core (or
  start with just 0 = erased, following Idris 2); check usage during
  elaboration; erase 0-quantity subterms at emission.

  Success: =Vec= length indices and equality proofs erase; the
  emitted/evaluated code carries no proof overhead. This tests Track
  B's QTT direction cheaply and serves the "useful system" bar
  directly (performance of resulting programs). Note: erasure *is* a
  stage distinction — connects to the staging thread.

  Result (2026-10-07): Basic mechanism complete. =(0 x : T)= syntax
  marks erased binders; the =erased= flag threads from surface
  through PreTerm to core Term (tPi/tSi/tLam). Pretty-printer shows
  =Pi(0 ...=. Full usage checking (reject erased var in relevant
  position) and codegen erasure are future work.

  References:
  [[https://github.com/raven6941/notes/blob/main/quantitative-type-theory.org][QTT vision and practice
  (McBride 2016; Brady 2021)]]; [[https://github.com/raven6941/notes/blob/main/alternative-cores.org][alternative
  cores]].

* Experiment 10 (complete 2026-10-07, basic) — e-graph conversion cache

  Question: can equality saturation memoize conversion without
  replacing NbE?

  Build: one e-graph per module over elaborated terms; every
  =areEqual(t1, t2)= first probes e-class membership (O(α) hit skips
  NbE); on miss, run NbE as the oracle and on success merge the
  e-classes. Sound by construction — the e-graph only remembers
  equalities NbE proved. Extension: user-proved propositional lemmas
  as conditional rewrite rules (Lean-egg style), undischarged
  side-conditions becoming holes.

  Success: measurable compile-time speedup on conversion-heavy
  elaboration; no behavior change on any existing test. Lowest-risk
  e-graph experiment in the program; do before any saturation-based
  elaboration. Honest costs: iteration bounds (fall back to NbE),

  Result (2026-10-07): Basic memo table complete (src/egraph.nim).
  convElab probes cache before NbE; on miss, runs NbE and merges on
  success. Key includes ctx length for soundness. Observed: 97 hits,
  38 misses on Vec-heavy test (no behavior change). Full e-class
  merging with union-find across different keys is future work —
  currently a memo table, not yet a true e-graph.
  first-order binder encoding, no why-not explanations.

  Round-4 extension (2026-10-07): *negative caching via
  die-graphs* (Zakhour et al., POPL 2025). When NbE *refutes*
  =t1 ≡ t2= (different head constructors), record a disequality
  edge between the e-classes instead of a bare miss — congruence
  propagates ≠ for free and later merge attempts are immediate
  contradictions. Turns the cache from positive-only into a
  decider with pruning power.

  Round-3 additions (2026-10-07): (a) index the equation/rule set in
  a matching triemap (Peyton Jones & Graf 2023) keyed by LHS patterns
  — one traversal per probe, returns all applicable rules with
  substitutions, α-aware; also the natural index for the
  elaborator's rewrite-rule set generally. (b) Witness-carrying
  merges (Kmett-style annotated union-find): each union stores its
  justification, turning the cache into a proof-producing structure
  and attacking the no-why-not blocker. Longer-term: permutation-
  annotated union-find for α-absorption of e-classes (binder problem).

  References:
  [[https://github.com/raven6941/notes/blob/main/egraph-conversion-cache.org][e-graph conversion cache]];
  [[https://github.com/raven6941/notes/blob/main/willsey-egg-2021.org][egg (Willsey et al.)]];
  [[https://github.com/raven6941/notes/blob/main/rossel-lean-egg-2026.org][Lean-egg]];
  [[https://github.com/raven6941/notes/blob/main/elaboration-as-saturation.org][elaboration as saturation]]
  (the ambitious sibling — research bet, not engineering).

* Track B — alternative cores (decision gate before Experiment 3)

  Experiments 1–2 are core-independent; 3–5 are core-sensitive
  (unification, reduction, and inductives all depend on the core's
  equality and datatype story). Before investing in 3–5, evaluate
  whether ETT is still the right core — see
  [[https://github.com/raven6941/notes/blob/main/alternative-cores.org][the alternative-cores note]].

  Candidates, in evaluation order: Observational Type Theory
  (ETT-done-right, same lineage), containers/polynomial functors (as
  the datatype mechanism), cubical type theory (if HITs become a
  goal), Quantitative Type Theory (if erasure/linearity becomes a
  goal). They compose; the criterion is which core makes the wanted
  surface features expressible and elaborable.

* Track C — relational × staged interpreters (language-design test-bed)

  Question: can one relational spec of the language yield many
  efficient tools — evaluator, checker, synthesizer — via staging, so
  that iterating on the language design stays cheap?

  Background: write the interpreter as a relation (=evalᵒ= à la Byrd,
  Holk & Friedman 2012) and each *direction* of the relation becomes a
  different tool; stage each direction into efficient code à la Amin &
  Rompf 2018 (a direction is a "modified semantics"; staging it is the
  Futamura move). See
  [[https://github.com/raven6941/notes/blob/main/relational-staged-interpreters.org][the concept note]].

  Round-3 bridge (2026-10-07): egglog already unifies relations +
  union-find; Kmett's annotated union-find (groupoid relation
  algebra) is the same algebraic shape. A relational interpreter
  whose equality relation is a groupoid-annotated union-find would
  let *one* structure serve evaluation, unification, and saturation
  — the Track C vision with the Experiment 10 machinery as its
  substrate.

  Aaron's substrate idea (2026-10-07): implement the =evalᵒ=
  relation over a union-find where reduction steps are unions and
  values are e-class annotations (Kmett-style: =find= returns
  (representative, value)) — "when =e_i ~> e_j= and =e_j= goes to
  =val_m=, =e_i= goes there directly" by path compression. This is
  e-class analyses (egg) and tabling (SLG) as one mechanism; value
  conflicts on union *detect* non-confluence. Forward and synth
  directions share the memoization.

  Build, in order:
  1. Relational ETT evaluator in Nim: =evalᵒ(term, env, value)= with
     logic variables, unification, =fresh=/=conde=. Directions:
     forward evaluation; backward synthesis (programs from values).
     Substrate: µKanren-style stream kernel (portable, no Prolog
     runtime).
  2. Relational typing: =typeᵒ(term, ty, ctx)=. Modes: infer (term →
     ty), check (term × ty → bool), synth (ty → term, i.e. proof
     search).
  3. Stage each mode with Nim macros: the relation is the single
     source; generate per-mode efficient implementations at compile
     time. Reference implementation: multi-stage miniKanren
     (Ballantyne et al., PLDI 2025) — =gather= vs =fallback=
     for staging-time non-determinism, =later= for staging-time
     termination, holes in interpreted programs. Compare
     staged-check against the hand-written =infer= from
     Experiment 2 on performance and error quality.
  3b. Table the relations (Kudasov's canonical bank over the
     µKanren kernel): memoize against canonical fresh variables,
     =prune= by observational key. This is also the
     =research[T]= subproblem cache — persist the table across
     compilations, content-addressed.
  4. Iteration test: extend the relation with a new construct,
     re-stage, confirm evaluator + checker + synthesizer all update.
  5. Compile-time synthesis with spec-hash cache (Aaron's idea,
     2026-10-07): a =synth"..."= macro — declare properties as a
     relation query, search at macro-expansion time, splice the
     witness as if hand-written. Cache witness-by-spec across
     compiles, keyed on the hash of the specification *plus the
     transitive closure of the relation definitions* (Nix-style
     dependency hashing; stale-relation ⇒ stale-witness is the
     correctness hazard). Canonical witness ordering required so
     the cache is a function of the spec.

  Success: one spec change propagates to all tools; staged tools
  within a small constant of hand-written ones; a synthesis demo
  (e.g. synthesize =pairSwap= from its type).

  Relationship to the main line: feeds Experiments 2–3 (infer/check
  are modes of one relation; unification *is* relational), Experiment
  6 (synth mode = tactic search), Experiment 7 (synthesis as an IDE
  tool). Start after Experiment 2 lands, in parallel with 3.

  References:
  [[https://github.com/raven6941/notes/blob/main/byrd-relational-interpreters.org][Byrd et al. 2012]];
  [[https://github.com/raven6941/notes/blob/main/amin-rompf-collapsing-towers.org][Amin & Rompf 2018]] §8
  (stage polymorphism via type classes — the =Sym[R]= analogy);
  [[https://github.com/raven6941/notes/blob/main/brown-palsberg-typed-self-evaluation.org][Brown & Palsberg 2017]]
  (the typed endpoint).

* Cross-cutting concerns (all experiments)

  - *Error messages.* Surface terms, source locations. Our =Term=s need
    location info from day one of Experiment 2 — Turnstile's emphasis,
    and easy to under-invest in.
  - *Phase discipline and performance.* Measure compile-time elaboration
    cost as programs grow; know what runs at expansion time vs. runtime.
  - *Reuse audit.* What of Nim's infrastructure do we actually reuse
    (hygiene via =gensym=/=inject=, source locations) vs. reimplement
    (everything type-related)? Compare honestly with Turnstile's reuse
    story.
  - *The convincing bar.* A small Software-Foundations-style corpus —
    Turnstile+ did volume 1 in Cur; even a fragment of one is a strong
    signal. Include an *annotation-burden measurement* (proposed
    2026-10-07): port the Dunfield & Krishnaswami "annotations only at
    redexes" discipline and measure how much the user must write over
    the corpus — the most direct operationalization of "useful system
    anyone would want to use".

* Explicit non-goals

  - Reusing Nim's *type system* for dependent checking. Like Racket (which
    is untyped), the host contributes syntax, staging, and tooling — the
    dependent checker is ours.
  - Universe polymorphism / cumulativity. ETT has =? : ?=; that's enough
    rope for now.

* Experiment 13 (possible future, 2026-10-07) — functorial datatypes

  Question: can Eponym's =data= declarations expose their
  polynomial-functor structure?

  Motivation (Aaron, 2026-10-07): PolyTT (Topos Institute) makes
  polynomial functors native to the type theory. The same structure
  models datatypes (containers, W-types) and interaction (dynamical
  systems, open games). If the theory speaks polynomial functors
  natively, reasoning about code and reasoning about domains share
  structure — a unifying substrate.

  For Eponym: our =data= desugarer already generates eliminators
  (catamorphisms). The experiment is to make the functorial
  structure *explicit* — generic map/fold/traverse derived from the
  functor, not generated per-type. Composition of datatypes via
  functor composition.

  Not a core replacement (PolyTT is experimental; our bottleneck is
  equality, not datatype genericity). A design influence: take the
  idea (functorial datatypes) without adopting the theory.

  See notes: [[https://github.com/raven6941/notes/blob/main/polynomial-functors-unifying-substrate.org][polynomial functors as unifying substrate]].

* Experiment 12 (complete 2026-10-07) — propositional equality

  Question: can Eponym express and prove equalities?

  Motivation: Idris/Lean boundary probe (2026-10-07). The
  =plusReducesZ : (n : Nat) -> n = plus n Z= example is small,
  self-contained, and currently impossible — no =Eq= type. Equality
  unlocks the most examples per unit of implementation.

  Build: =data Eq (A : ?) (x : A) : A -> ? where | refl : Eq A x x=
  (or via =postulate=). The eliminator J: transport along proofs.
  =cong= as a derived lemma. Must interact correctly with conversion
  (Experiment 5b): =refl= should typecheck when the sides are
  convertible, not just syntactically equal.

  Success: =plusReducesZ= elaborates and the proof computes. The
  broken-append diagnostic (Experiment 5b follow-up) still rejects
  with a good error.

  Result (2026-10-07): Complete. The existing =data= machinery
  handled =Eq= directly — no new elaborator code needed. =refl=
  typechecks up to conversion (Experiment 5b); J (=eqElim=) is
  auto-generated; =cong= derived; =plusReducesZ= proves by induction
  with =cong suc= in the step case. Tests in =src/elab.nim=,
  example in =examples/12-eq-plusReducesZ.ep=.

* Experiment 11 (complete 2026-10-07) — primitive efficient types

  Question: can Eponym have machine-efficient numbers without
  giving up the inductive core?

  Motivation (Aaron, 2026-10-07): unary =s(s(z))= in papers "screams
  that we aren't talking about something we expect people to actually
  use." A convincing system needs efficient numbers at the surface.

  Build: =postulate Int : ?= with integer literals and primitive
  operations (=+, -, *, ...=) that reduce via the =wRed= machinery
  (Experiment 4). The core keeps its simple inductive types for
  metatheory; the surface elaborates literals to the primitive.

  Success: =42 + 17= computes to =59= via the primitive reduction;
  the core's =data Nat= still works for proofs. No unary in
  surface examples.

  Result (2026-10-07): Complete. Added =wInt=/=tInt= to core for
  integer literals, =wPrim=/=tPrim= for primitive ops (addInt, subInt,
  mulInt) that compute via host operations. Parser handles integer
  literals (single =1= remains unit type for backward compat).
  =42 + 17= reduces to =59=; =data Nat= coexists for proofs.
  Tests in =src/elab.nim=, example in =examples/13-primint.ep=.

  Note: binary naturals via =data= (Experiment 5 follow-up,
  demonstrated 2026-10-07) show the mechanism generalizes beyond
  unary, but primitives are the real usability answer.
